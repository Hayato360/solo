### 1. Fighter permanently slow (CONFIRMED, FIXED)

**Symptom (user):** "when start fighter always walk so slow".

**Reproduced exactly.** Hold block → swap away while still holding → release. The old Fighter was left
`walkSpeed = 7.20`, `IsBlocking = true` and `BlockBaseWalkSpeed = 16` **forever**. Being stuck
`IsBlocking` also meant permanent 75% damage reduction — a hidden balance bug on top of the visible one.

**Cause:** three systems each mutated `Humanoid.WalkSpeed` in place — stats (`Speed`), stun (`= 0`) and
block (`*= 0.45`). Block also saved its base only on the first call, so repeat calls compounded. On a
swap the client fires `SetBlocking(false)` against the **new** rig, so the old one was never restored,
and the client's own `blocking == value` guard then suppressed the release event.

**Fix — speed is now DERIVED, never accumulated:**
- `RigFactory.ApplyCombatStats` and `Hunter.RefreshStats` publish `BaseWalkSpeed`.
- New `HumanoidUtil.RefreshWalkSpeed(rig)`: `base × (stunned and 0 or 1) × (blocking and 0.45 or 1)`.
  Idempotent — any order, any number of calls, same result.
- `Hunter.SetControlled(false)` clears block state and refreshes, so nothing strands on a swap.
- Lives in `HumanoidUtil` (shared) so a Class can call it without requiring a Service.

**Verified:** same scenario now leaves Kang at `walk = 16.00, blocking = false`.

### 2. Equipping a weapon made the player unable to attack (CONFIRMED, FIXED)

**Symptom (user):** "click when equip not animation anymore".

**Reproduced with companions silenced:** with `Sword01` equipped, two left clicks produced
**zero attacks started and zero damage**. An earlier reading of 666.9 damage was misleading — it was
entirely AI companion damage hitting the same dummy.

**Cause:** a Roblox `Tool` captures `MouseButton1`. The input reaches `InputBegan` with
`gameProcessed = true`, and the handler discards it. The sword is purely a visual, so equipping a weapon
silently disabled clicking to attack.

**Fix:** `CombatController` now hooks `Tool.Activated` as an equal attack trigger, re-hooking on
`ChildAdded` (the Tool is attached after the swap) and on every `Character` change.

### 3. Attack animations cut short by stale stop timers (FIXED)

`CombatFX` caches one track per animation per rig; `CombatService` also scheduled `track:Stop()` after
each attack. Because the track object is reused, an earlier swing's delayed stop could cut a later one
short. Attack tracks are already retimed to end exactly on the attack's length, so the forced stop was
removed (looping guard tracks still stop explicitly).

### 4. Overlapping stuns (HYPOTHESIS — TESTED AND WRONG)

Predicted WalkSpeed would strand at 0 when combo hits overlap. **Measured: restored correctly.** Did not
"fix" it. Did harden it anyway while rewriting: `stunEndsAt` tracks the furthest end time, so a longer
stun wins and an earlier timer cannot clear it early.

### 5. Latent integration gap with Codex's sword (FIXED)

`AttackDefs.WeaponCombos` selects a chain via the rig's `EquippedWeaponId` attribute — which nothing
ever set. Per-weapon combos would have silently never triggered once animations existed.
`Hunter.SetEquippedWeapon` now sets it for every weapon.
