## Issues Encountered

- **The old porting note was wrong.** It said "Hit and Block are R6". Measured on this place's rigs:
  **Hit works fine (0.52s)**; only **Block** fails — its length stays 0 even after `PreloadAsync`.
  The R6 thing in the note is `latestTest.Workspace.Dummy`; the `Rig` that the combat animations were
  authored against is the **same R15 constraint rig this place generates** (0 Motor6D, 15
  AnimationConstraints), which is why they transfer cleanly.
- **`AnimationTrack.Length` is 0 until the asset downloads.** My first verification concluded all six
  animations were unusable ("length=0.00s, NO VISIBLE MOTION") purely because I measured immediately
  after `LoadAnimation`. With `PreloadAsync` and a wait loop, five of six were fine.
  **This nearly caused a correct port to be abandoned as broken.**
- **The same bug lurked in the shipping code:** `AdjustSpeed(length / duration)` with `length == 0`
  yields speed 0 and freezes the track on frame one. Guarded, plus startup preloading.
- **`LoadAnimation` per swing leaks tracks** and re-downloads; `CombatFX` now caches per Animator.
- An atomic `multi_edit` failed because I anchored on `local Slots` (that is in `ItemDefs`, not
  `AttackDefs`). Nothing was applied, so it was a clean retry — atomic edits fail safe.

## Session Continuation — 01:30 (block pose)

**Request:** a Block animation — two hands guarding at the chest.

### What happened

1. Found `AnimationConstraint.Transform` is writable on these rigs and tried to author the guard purely
   in code (`Modules/BlockPose` + `CombatDefs.BlockPose` + a `CombatController` RenderStep binding).
2. **It does not work.** Reading the property straight back after writing returns identity. Verified with
   the `Animate` script **disabled** and **zero tracks playing** — still reverted. The engine owns that
   property; a script cannot hold a pose through it.
   - A screenshot early on appeared to show the arms posed, which was misleading: that was a combo
     animation mid-swing, not the pose. **The pcall "WRITABLE" check was also misleading** — the write
     does not error, it simply does not persist.
3. Removed `Modules/BlockPose`, its config block and its controller wiring rather than ship dead code.
4. Authored the pose instead as a **KeyframeSequence** at `ServerStorage.AnimationSources.BlockGuard`:
   looping, `Action2` priority, full R15 pose hierarchy, both arms raised with the forearms crossed in
   front of the chest.
5. Wired `CombatService.SetBlocking` to play and stop that track, keyed off `AttackDefs.Reactions.Block`.
   It is a **no-op until an id is published**, so blocking mechanics are unaffected meanwhile.

### Verified

- Raise/drop guard still accepted, `IsBlocking` toggles, WalkSpeed restored to 16.
- Clean boot, no errors, with the animation hook in place and no id set.
