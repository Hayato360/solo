คำคืออะไรตัวอย่างจริงในเพลส
Config ตารางข้อมูลล้วน ไม่มีฟังก์ชัน ไม่มี state ใช้เก็บ “ตัวเลขที่ปรับได้” การบาลานซ์เกมควรแก้ที่นี่ที่เดียว RoleDefs, GateDefs, ItemDefs (16 ไฟล์)
Class แม่แบบของสิ่งที่ “มีได้หลายตัวพร้อมกัน” แต่ละตัวเก็บ state ของตัวเอง และต้องมี :Destroy() Gate, Hunter, Monster, DungeonInstance (7 ไฟล์)
Service ระบบเดียวต่อเซิร์ฟเวอร์ (singleton) เป็นเจ้าของอายุของ Class ที่มันสร้าง มีเมธอด Init() และ Start() GateService ถือ Gate ทั้งหมด, PartyService ถือ Party (20 ไฟล์)
Controller Service ฝั่ง Client ดูแล UI กับ input อย่างเดียว ไม่ตัดสินผลเกม PartyController, QuestController (15 ไฟล์)
Remote ช่องทางเดียวที่ Client คุยกับ Server ได้ RemoteEvent = ส่งอย่างเดียว, RemoteFunction = ส่งแล้วรอคำตอบ Remotes/Gate/EnterGate (RemoteFunction คืน ok + ข้อความ)
Attribute ค่าที่แปะบน Instance แล้ว Roblox replicate ให้ Client เอง ใช้แทนการยิง Remote ถี่ ๆ Gate model มี Stability, SecondsLeft, GateState
Signal อีเวนต์ภายในฝั่ง Server ใช้ให้ระบบคุยกันโดยไม่ต้อง require กันตรง ๆ GateService.GateStabilityZero → DungeonBreakService รับไปเริ่มเหตุการณ์
กฎที่ทำให้โค้ดไม่พัง: Service เท่านั้นที่เรียก .new() และ :Destroy() ของ Class ระบบอื่นต้องขอผ่าน Service (เช่น GateService.GetGate(id)) ห้ามเก็บ reference เอง ไม่เช่นนั้นเมื่อ Gate ถูกลบจะเหลือ reference ค้าง

Server Bootstrap

ทำไมต้อง Init ทุกตัวก่อน แล้วจึงค่อย Start

Bootstrap วน 3 รอบ: รอบ 1 require ทุก ModuleScript ตาม SERVICE_ORDER, รอบ 2 เรียก Init() ทุกตัว, รอบ 3 เรียก Start() ทุกตัวด้วย task.spawn

เหตุผล: Init() คือที่สำหรับ ต่อ Signal และผูก dependency ส่วน Start() คือที่สำหรับ เริ่มสร้างของจริง (spawn Gate, spawn ปาร์ตี้) ถ้าใครไป connect signal ใน Start() จะพลาดอีเวนต์แรกที่เกิดจาก Service ที่ Start ไปก่อนแล้ว — บั๊กนี้เคยเกิดจริงกับ HunterAIService ที่พลาดปาร์ตี้แรก

-- ลำดับจริงใน SERVICE_ORDER (20 ตัว) DataService → PlaceholderCombatService → StatsService → PartyService → HunterAIService → GateService → GuildBaseService → DungeonBreakService → WalletService → DungeonService → ProgressionService → InventoryService → CraftingService → BlacksmithService → ClassService → QuestService → RecruitService → DummyService → TestHazardService → DebugService

ลำดับนี้ไม่ได้สุ่ม: DataService ต้องมาก่อนเพราะ PartyService อ่านปาร์ตี้จาก profile, GateService ต้องมาก่อน DungeonService เพราะ Dungeon ไปลงทะเบียน entry handler กับ Gate, และกลุ่ม progression/item/class/quest อยู่ท้ายเพราะทุกตัวฟัง Signal ของระบบก่อนหน้า

ทุก require และ Init ถูกห่อด้วย pcall — Service ตัวเดียวพังจะไม่ทำให้ทั้งเซิร์ฟเวอร์ตาย แต่จะขึ้น warn แทน และถ้ามีไฟล์ใน Services/ ที่ไม่อยู่ในลิสต์ ระบบจะเตือนว่ามันจะไม่ถูกสตาร์ต

Client Bootstrap

ข้อมูลต้องมาก่อนเมนูและ gameplay UI

-- ลำดับจริงใน CONTROLLER_ORDER (15 ตัว) GuiController → DataController → MenuController → CameraController → CharacterController → PartyController → GateController → DungeonController → DungeonBreakController → PartyEditorController → InventoryController → WorkshopController → ClassController → QuestController → RecruitController

GuiController มาก่อนสุดเพราะเกมตั้ง CharacterAutoLoads = false ทำให้ Roblox ไม่ copy StarterGui เข้า PlayerGui ให้อัตโนมัติ ต้องทำเอง

ถัดมาคือ DataController ซึ่งรับ Snapshot กับ KeyChanged แล้วเก็บสำเนา profile ไว้ในเครื่อง controller ที่เหลือ (bag, party editor, class, quest, recruit) อ่านจากสำเนานี้ ไม่ต้องยิง Remote ถามซ้ำ

ถ้า snapshot ถูกส่งมาก่อน controller จะ connect ทัน DataController จะเรียก GetSnapshot (RemoteFunction) ดึงย้อนหลังเอง — กันปัญหา race ตอนโหลด

โครงสร้างเดียวกันทั้งสองฝั่ง: ทั้ง Bootstrap และ ClientBootstrap ใช้ pattern เดียวกันเป๊ะ (ลิสต์ลำดับ → require + pcall → Init ทั้งหมด → Start ทั้งหมด) อ่านตัวหนึ่งเป็น ก็อ่านอีกตัวออก

กฎโครงสร้างสำคัญ

ใครรับผิดชอบอายุของวัตถุ?

  • Service เป็นเจ้าของอายุ — GateService เท่านั้นที่ Gate.new() และ RemoveGate() ระบบอื่นขอผ่าน GetGate(id)
  • Class ต้องมี Destroy() ที่ disconnect connection ทุกตัว (เก็บไว้ใน self._connections) และทำลาย Instance ที่มันสร้าง
  • Composition ไม่ใช่ inheritance — Hunter และ Monster ต่าง “มี” AIBrain คนละตัว ไม่ได้สืบทอดจากคลาสแม่ร่วมกัน
  • ไม่มี subclass ต่อ role/rank/modifier — ความต่างมาจากข้อมูลใน Config ที่คลาสเดียวอ่าน เช่น GateDefs.Ranks["S"]
  • Class คุยออกข้างนอกด้วย Signal — gate.StabilityZero:Fire(gate) แล้ว Service ที่เป็นเจ้าของรับไปส่งต่อ
ทำไมต้องเข้มเรื่องนี้: Gate เกิดและตายตลอดเวลา (สูงสุด 4 ตัว, spawn ใหม่ทุก 90 วินาที) ถ้า connection ไม่ถูกตัดตอน Destroy จะเกิด memory leak ที่ค่อย ๆ ทำให้เซิร์ฟเวอร์ช้าลงในรอบยาว

ตัวอย่างเส้นทางข้อมูล

เมื่อผู้เล่นกด Enter Gate เกิดอะไรขึ้น (ทีละบรรทัดจากโค้ดจริง)

  1. Client: GateController เรียก GetGateInfo(gateId) (RemoteFunction) Server ตอบกลับด้วย rank, stability, วินาทีที่เหลือ, modifier, PartyPower ของผู้เล่นคนนั้น และ Risk ที่คำนวณจาก PowerCalc.RiskLevel แล้ว GatePanel เอาไปแสดง
  2. Client: ผู้เล่นกดปุ่ม Enter → เรียก EnterGate(gateId) สังเกตว่า Client ขอ ให้เข้า ไม่ใช่สั่งย้ายตัวเอง Client ไม่มีสิทธิ์ teleport
  3. Server (GateService) ตรวจ 4 ข้อ: gateId เป็น string จริงไหม → Gate ยังอยู่และสถานะเป็น Open ไหม → Hunter ที่ควบคุมอยู่ยังไม่ตายไหม → อยู่ห่างจาก Gate ไม่เกิน EnterDistance = 20 studs ไหม
  4. Server ส่งต่อให้ DungeonService.TryEnter ซึ่งตรวจอีกชั้น: ปาร์ตี้ไม่ wipe, ยังไม่ได้อยู่ใน Gate อื่น, Gate ยัง Open, rank นี้มี dungeon template, และยังมี slot ว่าง (สูงสุด MaxSlots = 20 ชุดพร้อมกัน)
  5. Server: Gate เปลี่ยนเป็น InProgress → clone template ไปที่ SlotOrigin (10000, 0, 0) ห่างกัน slot ละ 2000 studs (ไกลจาก overworld จนไม่กวนกัน) → สร้าง DungeonInstance → แปะ attribute InDungeon = true บนตัวผู้เล่น
  6. Server: DungeonInstance คุมทุกอย่างในนั้น — trigger ห้อง (เช็กทุก 0.25 วินาที), wave มอนสเตอร์ (Room 1 = 3 ตัว, Room 2 = 4 ตัว), ประตูที่เปิดเมื่อเคลียร์, บอส, และทางออก
  7. จบรอบ: DungeonService จ่ายรางวัล แล้วยิง Signal PlayerCleared ซึ่ง ProgressionService (EXP), InventoryService (ดรอป) และ QuestService (ความคืบหน้า) รับไปพร้อมกัน จากนั้นคืนปาร์ตี้ออกมาและปล่อย slot
ทางออกที่ไม่ใช่การเคลียร์ก็ถูกจัดการหมด: ออกเอง → Gate กลับเป็น Open และเสียความคืบหน้า · ปาร์ตี้ wipe → Gate โดนหัก stability 10% แล้วกลับเป็น Open · Gate แตกขณะอยู่ข้างใน → ถูกเด้งออกพร้อมข้อความ (เคสนี้ยังอยู่ในรายการรอทดสอบ)

กลไกเอกลักษณ์ของเกม

การสลับตัวละคร (Character Swap) ทำงานอย่างไร

นี่คือกลไกที่ยากที่สุดในโปรเจกต์และเป็นจุดที่เจอบั๊กมากที่สุด เพราะมันฝืนสิ่งที่ Roblox ตั้งใจให้เป็น หัวข้อนี้อธิบายตั้งแต่สิ่งที่ผู้เล่นเห็น ไปจนถึงสิ่งที่เกิดขึ้นจริงในหน่วยความจำ

สิ่งที่ผู้เล่นเห็น

กด 1, 2, 3 หรือคลิกรูป portrait บน HUD แล้วผู้เล่นก็ย้ายไปบังคับ Hunter อีกตัวทันที ตัวที่เพิ่งปล่อยจะกลายเป็น AI สู้ต่อเอง ส่วนตัวที่เพิ่งรับมาก็เดินตามคีย์ของผู้เล่นได้เลย

สิ่งที่เกิดขึ้นจริง

เกมไม่ได้ “ย้ายวิญญาณ” ผู้เล่นไปอีกร่าง แต่เปลี่ยนค่า player.Character ให้ชี้ไปที่ rig อีกตัวที่มีอยู่แล้วในโลก ทั้ง 3 rig ถูก spawn พร้อมกันตั้งแต่ต้นและอยู่ในโลกตลอดเวลา ไม่มีการสร้างหรือลบตอนสลับ

ปัญหาที่ทำให้เรื่องนี้ยาก: เมื่อ assign player.Character ตัวใหม่ Roblox จะ ทำลายโมเดลตัวเก่าทิ้งทันที ถ้าไม่ทำอะไรเลย Hunter ที่เพิ่งปล่อยจะหายไปจากเกมทุกครั้งที่สลับ

ทางแก้: ย้ายร่างออกก่อนแล้วปล่อยให้ทำลาย “เปลือกเปล่า”

Hunter:_detachFromCharacter() จะสร้าง Model ใหม่ขึ้นมา แล้วย้ายของทุกชิ้นจากโมเดลเดิมเข้าไป สิ่งที่ Roblox ทำลายจึงเหลือแค่เปลือกที่ว่างเปล่า

-- ลำดับสำคัญมาก 1. สร้าง Model ใหม่ 2. copy attributes ทุกตัว 3. copy CollectionService tags ทุกอัน 4. ย้ายลูกทุกตัว ยกเว้น Humanoid 5. ย้าย Humanoid เป็นอันสุดท้าย 6. ตั้ง PrimaryPart แล้วชี้ self.Rig ไปที่ Model ใหม่

ทำไม Humanoid ต้องย้ายท้ายสุด: ถ้าย้าย Humanoid เข้าไปก่อน มันจะอยู่ใน Model ที่ยังไม่มีชิ้นส่วนร่างกาย Roblox จะถือว่าร่างไม่สมบูรณ์และอาจสั่งให้ตาย

ข้อดีของวิธีนี้: ตัว Humanoid และ part ทุกชิ้นเป็น instance เดิม ไม่ได้ถูก clone ใหม่ connection ที่ต่อไว้ เช่น Humanoid.Died และ HP ปัจจุบัน จึงรอดมาทั้งหมด ไม่ต้องต่อใหม่

ลำดับเหตุการณ์เต็ม ตั้งแต่กดปุ่มจนกล้องตาม

  1. Client: PartyController จับปุ่ม 1/2/3 หรือคลิก portrait แล้วยิง Remotes/Party/RequestSwap พร้อมเลข slot — ส่งแค่ ตัวเลข ไม่ได้ส่งคำสั่งอะไรมากกว่านั้น
  2. Server (Party:RequestSwap) ตรวจ 5 ด่าน ตามลำดับ แล้วคืนเหตุผลถ้าไม่ผ่าน: ปาร์ตี้ wipe อยู่หรือเปล่า (Wiped) → slot นี้มีจริงไหม (InvalidSlot) → เป็นตัวที่บังคับอยู่แล้วหรือเปล่า (AlreadyActive) → ตัวเป้าหมายยังมีชีวิตไหม (Dead) → ผ่าน cooldown 1 วินาที แล้วหรือยัง (Cooldown)
  3. ปล่อยตัวเก่าก่อนเสมอ — previous:SetControlled(false): ลบสคริปต์ Animate ออกจาก rig → เรียก _detachFromCharacter() → คืน network ownership ให้ Server → จับตัวยืนตรงด้วย HumanoidUtil.Upright + Stabilize → เริ่ม RigAnimator ฝั่ง Server ให้เล่นอนิเมชันเดินแทน
  4. แล้วจึงรับตัวใหม่ — next:SetControlled(true): หยุด RigAnimator ฝั่ง Server → Owner.Character = Rig → SetNetworkOwner(player) ให้ผู้เล่นได้สิทธิ์ simulate → ใส่สำเนาสคริปต์ Animate กลับเข้า rig
  5. Client ตอบสนองต่อการเปลี่ยน: ทั้ง CameraController และ CharacterController ฟัง player:GetPropertyChangedSignal("Character") ตัวแรกตั้ง camera.CameraSubject เป็น Humanoid ตัวใหม่ ตัวหลังเรียก Upright + Stabilize ฝั่ง Client
  6. HUD อัปเดต: party.Changed ยิง → Server ส่ง PartyState ให้เจ้าของ → portrait ย้ายกรอบเน้นไปที่ slot ใหม่

ทำไมต้องมี Animate สองสถานะ

สคริปต์ Animate ของ Roblox ทำงานได้เฉพาะกับตัวละครที่ผู้เล่นควบคุม ตอน Hunter.new จึงดึงมันออกจาก rig เก็บไว้เป็น template (animateTemplate.Parent = nil)

ควบคุมอยู่ = ใส่สำเนา Animate เข้าไป ให้ Client เล่นอนิเมชันเอง · เป็น AI = ลบทิ้ง แล้วใช้ RigAnimator ฝั่ง Server แทน

ใครเป็นคน simulate ร่างไหน

Roblox ให้เครื่องที่ถือ network ownership เป็นคนคำนวณฟิสิกส์ของร่างนั้น rig ที่ผู้เล่นบังคับ = เครื่องผู้เล่น · อีก 2 ตัว = Server (RigFactory.SetServerOwned)

ถ้าไม่บังคับให้เป็นของ Server Roblox จะยกความเป็นเจ้าของของ rig ที่อยู่ใกล้ผู้เล่นให้ผู้เล่นโดยอัตโนมัติ ซึ่งทำให้ AI กระตุกและเปิดช่องให้โกง

บั๊ก FallingDown ที่ทำให้ดูเหมือนตาย

การย้ายร่างข้าม Model ทำให้ Humanoid ตกไปอยู่สถานะ FallingDown — ตัวละครล้มลงกับพื้น และตายได้จริงจากการตรวจ “คอหลุด”

HumanoidUtil จึงปิดสถานะ FallingDown และ Ragdoll ทิ้ง (การล้มจะมาจากระบบ combat ของเราเองใน Stage 5 เท่านั้น) และตั้ง RequiresNeck = false

จุดที่พลาดง่ายที่สุด: SetStateEnabled ของ Humanoid ไม่ replicate ข้ามเครื่อง แปลว่าเครื่องไหนเป็นคน simulate เครื่องนั้นต้องเรียก Stabilize เอง นี่คือเหตุผลเดียวที่ CharacterController ฝั่ง Client มีอยู่ — ถ้าตั้งแต่ฝั่ง Server อย่างเดียว rig ที่ผู้เล่นบังคับจะยังล้มอยู่ดี

สลับอัตโนมัติเมื่อตาย และการ wipe

สถานการณ์ระบบทำอะไรค่าในโค้ด
Hunter ที่กำลังบังคับตาย แต่ยังมีตัวอื่นรอด หน่วงเวลาสั้น ๆ ให้เห็นจังหวะตาย แล้ววนหาตัวถัดไปที่ยังมีชีวิต (_findNextAlive วนแบบวงกลม) แล้วสลับให้เอง หน่วง 0.6 วินาที
Hunter ตัวที่ไม่ได้บังคับตาย อัปเดต HUD อย่างเดียว ไม่สลับ ยิง Changed
ตายครบทั้ง 3 ตัว ตั้ง IsWiped = true แล้วยิง Wiped → PartyService ตั้งเวลา respawn · ถ้าอยู่ใน Gate DungeonService หัก stability 10% แล้วเด้งออก respawn ใน 5 วินาที
สลับตัวระหว่างที่ปาร์ตี้ wipe ปฏิเสธด้วยเหตุผล Wiped ด่านแรกของ RequestSwap

การหน่วง 0.6 วินาทีมี guard ซ้อนอยู่: ก่อนสลับจริงจะเช็กอีกครั้งว่าปาร์ตี้ยังไม่ถูกทำลาย ยังไม่ wipe และตัวที่บังคับอยู่ยังเป็นตัวที่เพิ่งตาย — กันกรณีที่ผู้เล่นกดสลับเองทันภายใน 0.6 วินาทีนั้น

ตำแหน่งตอน spawn: ทั้ง 3 rig เกิดเป็นรูปสามเหลี่ยมรอบจุด origin — (0,0,0), (-5,0,5), (5,0,5) — และ slot 1 เป็นตัวที่ถูกควบคุมเสมอ

ข้อจำกัดตอนทดสอบ: ระบบจำลองคีย์บอร์ดผ่าน MCP กดปุ่ม 1 ไม่ได้ การทดสอบสลับไปยัง slot 1 จึงต้องกดเองหรือใช้การคลิก portrait แทน

สูตรคำนวณจริง

ตัวเลขในเกมมาจากไหน

สามสูตรนี้คือหัวใจของการบาลานซ์ทั้งเกม ทุกอย่างที่เหลือต่อยอดจากสามตัวนี้

1. พลังของ Hunter

อยู่ใน Modules/StatCalc.HunterStats ซึ่งทั้ง Server และ UI ฝั่ง Client เรียกตัวเดียวกัน

growth = (1 + 0.06 x (Level-1)) x RarityStatMultiplier HP = RoleDefs.HP x growth ATK = RoleDefs.ATK x growth DEF = RoleDefs.DEF x growth แล้วบวก Flat (เกียร์) ก่อน คูณ Multiplier (Player Class) Power = ATK x 2 + DEF + HP / 10

ลำดับสำคัญ: บวกก่อน คูณทีหลัง เกียร์ให้ค่าแบบ flat ส่วน Player Class ให้แบบคูณ คลาสจึงยิ่งแรงขึ้นเมื่อผู้เล่นมีเกียร์ดี

2. Stability ของ Gate

อยู่ใน Classes/Gate.Tick ถูกเรียกทุกเฟรมจาก GateService

-- ต่อวินาที drain = 100 / (StabilityMinutes x 60) x StabilitySpeed x playerScale playerScale: 0 คน = 0 (หยุดนิ่ง) 1-2 คน = 0.5 3 คนขึ้นไป = 1 Stability = max(floor, Stability - drain x dt)

floor ปกติเป็น 0 แต่จะกลายเป็น 5% เมื่อมี break อื่นทำงานอยู่ หรือยังติด cooldown 300 วินาที — Gate อื่นจึงค้างที่ 5% รอคิว ไม่แตกพร้อมกันหมด

3. EXP และ Rank

อยู่ใน ProgressionDefs + StatCalc.ExpToNext

-- EXP ที่ต้องใช้ขึ้นเลเวลถัดไป ExpToNext(L) = floor(100 x L ^ 1.5) Lv 1 → 2 : 100 Lv 10 → 11 : 3,162 Lv 49 → 50 : 34,300 -- ฆ่ามอนสเตอร์ ทั้งปาร์ตี้ได้ KillExp x RankMultiplier คนที่ลงดาบสุดท้ายได้เพิ่มอีก 50%

Hunter Rank ไม่ได้ขึ้นกับเลเวลอย่างเดียว ต้องผ่าน ทั้ง เลเวลขั้นต่ำ และ จำนวน Gate ที่ผู้เล่นเคลียร์สะสม

219 นี้ตัดสินอะไรบ้าง:
· Risk ที่แสดงบน GatePanel — เทียบกับ RecommendedPower ของ Gate: ≥100% = Safe, ≥70% = Risky, ต่ำกว่านั้น = Dangerous
  Gate E (100) → 219% = Safe · Gate D (200) → 110% = Safe · Gate C (400) → 55% = Dangerous
· Gate rank cap — Gate จะ spawn ได้เฉพาะ rank ที่ RecommendedPower ≤ 219 × 1.5 = 328.5 ดังนั้นตอนนี้เกิดได้แค่ E และ D
· ถ้าผู้เล่นที่แข็งที่สุดออกจากเกม Gate ที่เกิน cap จะ หยุดนับ stability ทันที (ยกเว้น rank E ที่ไม่มีวันหยุด)

ตารางค่าปรับแต่ง

ค่าทั้งหมดที่คัดมาจาก Config จริง

ทุกตารางข้างล่างอ่านตรงจาก ReplicatedStorage.Config ในเพลส ถ้าจะบาลานซ์เกม แก้ที่ไฟล์เหล่านี้ไฟล์เดียวพอ ไม่ต้องไปตามแก้ใน service — กดแท็บเพื่อสลับตาราง

สัญญาระหว่างระบบ

ช่องทางสื่อสาร 3 แบบ และใช้ตอนไหน

ความปลอดภัยของเกม

ทำไม Client แก้ Gold หรือดาเมจเองไม่ได้

Client รับปุ่มและแสดงผล แต่ไม่ใช่แหล่งความจริง ทุก Remote handler บน Server ตรวจก่อนเสมอ ตัวอย่างจริงที่อ่านได้จากโค้ด:

  • ตรวจชนิดข้อมูล — if typeof(gateId) ~= "string" then return false end ทุกตัวแปรที่รับจาก Client
  • ตรวจระยะ — เข้า Gate ต้องอยู่ใน 20 studs, ใช้โครงสร้างในฐานต้องอยู่ใน StructureRange 18 studs
  • ตรวจความเป็นเจ้าของ — สลับ Hunter ได้เฉพาะในปาร์ตี้ของตัวเอง, ใส่เกียร์ได้เฉพาะ Hunter ที่ตัวเองมี
  • ตรวจสถานะเกม — เปลี่ยนปาร์ตี้ไม่ได้ตอน InDungeon, ใช้โครงสร้างไม่ได้ตอนฐาน Damaged
  • ตรวจก่อนหักเงิน — craft และ upgrade เช็ก Gold และวัสดุให้ครบก่อน แล้วจึงหักทั้งคู่ (all or nothing)

ข้อมูลถาวรไหลผ่าน DataService ที่เดียว ซึ่งเป็นโค้ดชิ้นเดียวในเกมที่แตะ DataStore ระบบอื่นเขียนผ่าน Set / Update / Increment เพื่อให้ทุกการเปลี่ยนแปลง replicate อัตโนมัติ

dependency ที่ตั้งใจให้เปลี่ยนได้

จุดที่ออกแบบไว้ให้ถอดเปลี่ยนทีหลัง

Combat (Stage 5): ตอนนี้ดาเมจทั้งหมดผ่าน PlaceholderCombatService ตัวเดียว Stage 6 ไม่ได้ยุ่งกับสูตรดาเมจเลย แต่ส่งค่าผ่าน attribute บน rig แทน (ATK, DEF, MaxHealth, HealingMultiplier, RegenMultiplier) นักพัฒนาที่รับ Stage 5 จึงเปลี่ยนเป็น CombatService จริงได้โดยไม่ต้องแก้ระบบอื่น

ExtrasProvider: PartyService.RegisterExtrasProvider(fn) คือจุดเสียบ stat bonus ตอนนี้มีสองเจ้าลงทะเบียนอยู่ — InventoryService (เกียร์ = flat) และ ClassService (คลาส = multiplier) ระบบใหม่ในอนาคตเสียบเพิ่มได้โดยไม่ต้องแก้ StatCalc

EntryHandler: GateService.SetEntryHandler() ทำให้ GateService ไม่ต้อง require DungeonService เลย — ตัดวงจร dependency แบบวนกลับ

ต้องเอาออกก่อนปล่อยจริง: DebugService (รับคำสั่งจาก attribute ของผู้เล่น), DummyService (หุ่นซ้อม) และ TestHazardService (Death Box) ทั้งสามตัวอยู่ท้าย SERVICE_ORDER อยู่แล้ว จึงลบชื่อออกจากลิสต์ได้ตรง ๆ

รายการที่ต้องทดสอบ

เปิด Studio แล้วไล่ตามลำดับนี้

เรียงให้ข้อที่ทำให้ฐานเสียหายอยู่ท้ายสุด เพราะมันจะล็อกโครงสร้างที่ข้ออื่นต้องใช้

  • 1. ขายของและถอดเกียร์จาก Bag (B) — ดู Gold และ stat ขยับ
  • 2. ใช้ potion (H) ตอน HP พร่อง — ควรฟื้น 40%
  • 3. วาง trap (T) ใกล้มอนสเตอร์ — ดูว่าดาเมจเข้าจริง
  • 4. รับ secret quest แล้วดูว่าขั้นตอนเดินหน้า
  • 5. recruit Hunter แล้วใส่ลงปาร์ตี้ใน party editor
  • 6. รอ / บังคับ quest board refresh แล้วดู rollover
  • 7. ทำให้ฐาน Damaged แล้วตรวจว่า prompt ทุกอันถูกปิด และซ่อมแล้วกลับมา
ค้างจาก Stage 3 ด้วย: Red Gate ที่ออกไม่ได้, มอนสเตอร์ Berserk, ปาร์ตี้ wipe แล้วโดนเด้ง, และ Gate แตกขณะที่ปาร์ตี้ยังอยู่ข้างใน — บางข้อรอ Stage 7 ก่อนถึงจะทดสอบได้ครบ
